# Generate Test Skill

대상 소스 코드를 분석하고, 테스트 코드를 체계적으로 생성한다.

```
Step 1. 대상 소스 코드 분석
Step 2. 테스트 케이스 설계
Step 3. 테스트 코드 생성
Step 4. 테스트 실행 및 검증
```

---

## Step 1. 대상 소스 코드 분석

테스트 대상 코드와 관련 의존성을 읽고 분석한다.

- 대상 클래스의 공개 메서드, 비즈니스 로직, 예외 발생 조건
- 의존하는 클래스와 인터페이스
- 프로젝트의 아키텍처와 컨벤션 (CLAUDE.md 참고)
- 기존 테스트 파일이 있으면 함께 읽어 컨벤션 파악

---

## Step 2. 테스트 케이스 설계

소스 코드 분석을 바탕으로, 테스트 유형별로 테스트 케이스를 설계한다.
**테스트 코드를 작성하기 전에, 설계 결과를 사용자에게 보여주고 확인을 받는다.**

### 테스트 유형

| 유형 | 목적 |
|---|---|
| **단위 테스트** | 클래스 단위의 로직 검증. 의존성은 mock 처리 |
| **통합 테스트** | 실제 의존성을 포함한 전체 흐름 검증 |
| **E2E 테스트** | 실제 HTTP 요청을 통한 엔드투엔드 검증 |

### 단위 테스트 범위 판단 기준

**단위 테스트에서 검증할 것**
- 조건에 따른 예외 발생 분기
- 조건에 따라 다른 로직을 실행하는 분기
- 비즈니스 규칙에 의한 판단/거부

**단위 테스트에서 검증하지 않을 것 → 통합 테스트로**
- mock 반환값을 DTO로 변환한 뒤 필드별 비교 (구현 추적)
- 단순 위임 호출 흐름
- `verify(save())`로 저장 호출 여부만 확인 (내부 구현 의존)

**판단 기준:** 분기/판단 로직이 없고 단순히 저장 후 변환하는 흐름이라면, 단위 테스트보다 **통합 테스트**가 적합하다.

### 설계 출력 형식

테스트 유형별로 테스트 메서드명을 나열한다.

```
### 단위 테스트: {Class}Test

- 존재하지_않는_상품_조회_시_예외가_발생한다
- 이미_발급받은_쿠폰을_다시_발급하면_예외가_발생한다

### 통합 테스트: {Class}IntegrationTest

- 상품_등록_조회_수정_삭제_전체_흐름을_검증한다
```

## Step 3. 테스트 코드 생성

사용자 확인 후, 설계된 테스트 케이스를 코드로 작성한다.

### 테스트 메서드 네이밍 규칙

**핵심 원칙: 테스트 메서드명은 비즈니스 의도(유비쿼터스 언어)로 작성한다.**

테스트 메서드명은 `{조건}_{행위}_시_{비즈니스_기대결과}` 형태로 작성한다.

**메서드명에 구현 상세를 넣지 않는다.**
구현 상세란 구현 메서드명, 예외 클래스명, 에러 코드, 컬럼명 등을 말한다.
구현이 바뀌면 테스트명도 바꿔야 하므로, 비즈니스 행위 기반으로 작성해야 리팩토링에 강하다.
구현 상세는 **assertion에서 검증**한다.

| 나쁜 예 | 좋은 예 | 이유 |
|---|---|---|
| `validateUsable에서_BAD_Request가_발생한다` | `사용_가능_여부_검증_시_예외가_발생한다` | 비즈니스 행위로 표현 |
| `calculateDiscount가_5000을_반환한다` | `정액_할인_쿠폰은_고정_금액을_할인한다` | 비즈니스 의미 표현 |
| `CoreException_NOT_FOUND가_발생한다` | `예외가_발생한다` | 예외 클래스·에러 코드는 assertion에서 검증 |
| `deletedAt이_설정된다` | `삭제_처리된다` | 컬럼명 대신 비즈니스 의미 표현 |
| `상품을_생성하면_성공한다` | `상품_생성_시_상품정보를_반환한다` | 구체적 결과 명시 |
| `실패한다` | `예외가_발생한다` / `400을_반환한다` | 구체적 실패 결과 명시 |

### 코딩 컨벤션

| 항목 | 규칙 |
|---|---|
| **구조** | given / when / then |
| **Assertion** | AssertJ (`assertThat`, `assertThatThrownBy`) |
| **Mocking** | BDDMockito (`given`, `willReturn`, `willThrow`, `verify`) |
| **메서드명** | 한글 + 언더스코어 (`void 메서드명()`) |
| **접근 제어자** | 테스트 클래스와 메서드에 접근 제어자 생략 (package-private) |

### 테스트 유형별 패턴

#### 단위 테스트

```java
// 의존성이 없는 경우 - 순수 단위 테스트
class ProductTest {
    @Test
    void 상품_정보를_변경하면_변경된_정보가_반영된다() {
        // given - 테스트 대상 객체 생성
        // when - 행위 수행
        // then - 상태 변화 검증
    }
}

// 의존성이 있는 경우 - mock 기반 단위 테스트
@ExtendWith(MockitoExtension.class)
class ProductServiceTest {
    @Mock
    private ProductRepository productRepository;

    @InjectMocks
    private ProductService productService;

    @Test
    void 존재하지_않는_상품_조회_시_예외가_발생한다() {
        // given - mock 설정
        // when & then - 예외 검증
    }
}
```

#### 통합 테스트

```java
@SpringBootTest
@Transactional
class ProductServiceIntegrationTest {
    @Autowired
    private ProductService productService;

    @Test
    void 상품_등록_조회_수정_삭제_전체_흐름을_검증한다() {
        // CRUD 전체 흐름을 하나의 테스트에서 검증
    }
}
```

#### E2E 테스트

```java
@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
class ProductE2ETest {
    @Autowired
    private TestRestTemplate restTemplate;

    @Test
    void 상품_생성_API_호출_시_201을_반환한다() {
        // given - 요청 데이터 준비
        // when - 실제 HTTP 요청
        // then - 응답 상태 코드 및 바디 검증
    }
}
```

## Step 4. 테스트 실행 및 검증

작성한 테스트를 실행하여 모든 테스트가 통과하는지 확인한다.

- 프로젝트의 빌드 도구에 맞는 명령어로 실행한다.
- 실패하는 테스트가 있으면 원인을 분석하고 수정한다.
- 모든 테스트 통과 후, 결과를 요약하여 사용자에게 보고한다.

### 결과 보고 형식

```
## 테스트 결과 요약

| 테스트 파일 | 유형 | 테스트 수 | 결과 |
|---|---|---|---|
| ProductTest | 단위 | 3개 | 통과 |
| ProductServiceTest | 단위 | 5개 | 통과 |
| ProductServiceIntegrationTest | 통합 | 2개 | 통과 |
```

---

## 공통 주의사항

1. 소스 코드를 읽지 않은 상태에서 테스트를 작성하지 않는다.
2. 기존 테스트 파일이 있으면 반드시 읽어 컨벤션을 따른다.
3. 테스트 메서드명에 "성공한다", "실패한다" 같은 모호한 표현, 구현 상세를 사용하지 않는다.
4. 테스트 코드 작성 전 반드시 Step 2의 설계 결과를 사용자에게 확인받는다.
5. 불필요한 테스트(getter 검증, 단순 위임, 반환값 필드 매핑 등)는 단위 테스트에서 작성하지 않는다.
