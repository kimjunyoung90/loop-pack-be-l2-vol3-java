## Q1. 대기열 자료구조 선택

**[질문]**
대기열을 구현할 때 Redis의 여러 자료구조 중 Sorted Set을 선택하셨는데요. Redis에는 List, Set, Sorted Set, Stream 등 다양한 자료구조가 있잖아요. List로도 FIFO 큐를 만들 수 있는데, 왜 Sorted Set을 선택했나요? List 대비 Sorted Set이 이 시나리오에서 어떤 이점을 주는지 설명해 주세요.

**[답변]**
> 클라이언트의 중복 요청을 방지하기 위해서 List 보다는 Set이 중요했다. 그리고 먼저 요청온 클라이언트의 요청을 먼저 처리하기 위해 순서 정보가 필요했고 이를 제공해야했다. 그래서 Sorted Set을 사용했다.

**[후속 질문: 순번 조회 시간복잡도]**
순번 조회 관점에서도 차이가 있습니다. 유저가 "나 지금 몇 번째야?"를 물어볼 때, List와 Sorted Set 각각에서 이 연산의 시간복잡도가 어떻게 다를까요?

**[답변]**
> List의 시간복잡도는 O(1)이다. index 기반 바로 조회가 가능하기 때문에 맞나?

**[후속 질문: List에서 userId 위치 찾기]**
List에서 index로 조회하려면 먼저 그 유저가 몇 번째 index에 있는지를 알아야 합니다. 유저가 "나 몇 번째야?"라고 물어왔을 때, List에서 특정 userId가 어디에 위치하는지 찾으려면 어떤 Redis 명령어를 써야 하고, 그 시간복잡도는 어떻게 될까요?

**[답변]**
> 나는 몰라.

**[정리]**
List에서 특정 값의 위치를 찾으려면 `LPOS` 명령어를 사용하는데, 이는 리스트를 순차 탐색하므로 O(N)이다. 반면 Sorted Set의 `ZRANK`는 skip list 구조로 O(log N)에 순번을 반환한다. 대기열에서 순번 조회는 유저가 2초마다 반복 호출하는 연산이므로 이 차이가 크다.

Sorted Set 선택 이유 정리:
1. 중복 방지 — Set 특성으로 자동 처리
2. 순서 보장 — score(timestamp) 기반 정렬
3. 순번 조회 성능 — ZRANK O(log N)

**[후속 질문: 해결 방법]**

**[답변]**
> ns를 사용하면 되겠네

**[정리]**

| 방식 | 충돌 가능성 | 특징 |
|------|------------|------|
| currentTimeMillis | 낮음 (ms 단위) | 현재 구현. 실용적으로 충분 |
| nanoTime | 매우 낮음 | JVM 내 단조 증가, 단 서버 간 비교 불가 |

## Q4. 토큰 TTL 설계

**[질문]**
현재 토큰 TTL이 ttl-minutes: 30으로 설정되어 있는데요. 이 30분이라는 값이 너무 길거나 너무 짧다고 느끼시진 않나요? TTL을 정할 때 어떤 점들을 고려해야 할까요?

**[답변]**
> 나도 모르겠어...

**[후속 질문: 극단적 상황 비교]**
TTL이 24시간이라면? 10초라면? 각각 유저 입장과 시스템 입장에서 어떤 일이 벌어질까요?

**[답변]**
> 유저가 안좋을게 있나??? 짧으면 기껏 기다렸는데, 주문을 못하겠지.

**[후속 질문: TTL이 길면 시스템 관점에서]**
토큰을 받은 유저 50명 중 30명이 이탈해서 주문을 안 하고 있다면, TTL이 길면 어떻게 될까요?

**[답변]**
> 30자리??

**[정리]**
TTL은 두 가지의 균형점을 찾아야 한다:

| TTL이 너무 짧으면 | TTL이 너무 길면 |
|-------------------|-----------------|
| 기다렸는데 주문 못하는 유저 발생 | 이탈한 유저의 자리가 오래 점유됨 |
| Token Conversion Rate 하락 | 뒤에 대기 중인 유저의 대기 시간 증가 |

실무에서는 3~5분 정도가 일반적. 주문 페이지에서 확인 후 결제까지 충분하면서, 이탈자의 자리를 빠르게 회수할 수 있는 범위. 현재 30분은 넉넉한 편이며, 근거를 갖고 조정이 필요하다.

**[후속 질문: 뒤에 있는 유저가 왜 대기하는가]**
> 왜 대기해??

**[추가 분석]**
현재 QueueScheduler 코드를 확인하면, 매 주기마다 활성 토큰 수와 관계없이 무조건 batchSize(50)명을 꺼내 토큰을 발급한다. 따라서 이 구조에서는 TTL이 길어도 뒤 유저의 대기가 직접 늘어나진 않는다.

다만 TTL이 긴 것의 실제 문제는: 이탈한 유저의 토큰이 만료되지 않고 쌓이면, 스케줄러가 계속 50명씩 추가 발급하므로 동시 활성 토큰 수가 계속 증가 → DB 커넥션 풀 압박으로 이어진다.

**[답변]**
> 하나는 발급량을 제어하는거고 하나는 소비량을 제어하는거네??

## Q7. Redis 장애 시 대응

**[질문]**
대기열의 핵심 인프라인 Redis가 죽으면 어떻게 해야 할까요?

**[답변]**
> 현재 서비스가 원활하지 않습니다. 잠시 후 다시 시도해주세요. 응답을 보내거나 메시지 브로커로 대기열을 변경하는 전략이 있어.

**[후속 질문: 블랙 프라이데이 중 장애라면]**
블랙 프라이데이 행사 중에 Redis가 죽었다면, 전면 차단과 메시지 브로커 Fallback 중 어느 쪽을 선택하겠어요?

**[답변]**
> 메시지 브로커지.

**[후속 질문: 이유]**
왜 메시지 브로커 쪽을 선택했나요?

**[답변]**
> 블랙 프라이데이 상황에서는 다수의 클라이언트가 상품 구매를 많이 하기 때문에 매출이 폭발적으로 증가하는 기간이야. 이 시점에 주문이 안된다면 회사 매출에 평소대비 끼지는 악영향이 비교할 수 가 없을 정도야. 때문에 대비책을 마련해두는게 좋지.

**[후속 질문: Fallback 상태에서 하류 보호]**
메시지 브로커로 Fallback하면 대기열 없이 주문 요청이 바로 들어오는 것과 비슷한 상황이 됩니다. 하류 시스템 보호는 어떻게 할 수 있을까요?

**[답변]**
> Fallback 상태에서 하류 보호는 서킷 브레이커 모듈에서 제공하는 Rate Limiter를 사용하면 될 것 같아.

**[정리]**
Graceful Degradation 전략:

```
정상 상태:  대기열(Redis) → 토큰 → 주문 API
장애 상태:  Rate Limiter → 주문 API (순번 없이, 처리량만 제한)
```

블랙 프라이데이처럼 비즈니스 임팩트가 큰 시점에는 서비스 품질이 떨어지더라도(순번 조회 불가, 공정성 약화) 매출을 지키는 판단이 합리적이다. 핵심은 "장애 시 어떻게 동작할 것인가"를 사전에 정의해두는 것 자체가 중요하다.

| 방식 | 장점 | 단점 |
|------|------|------|
| Controller에서 명시 호출 | 흐름이 눈에 보임, 어떤 API가 검증하는지 명확 | API 추가 시마다 코드 반복 |
| Interceptor | URL 패턴만 등록하면 자동 적용, 중복 제거 | 흐름이 숨겨짐, 설정 파일을 봐야 함 |

토큰 검증이 주문 API 하나에만 필요하다면 Controller 명시 호출로 충분. 2~3개 이상으로 늘어나는 시점에 Interceptor로 추출하면 된다.

추가 설명:
- Filter: Servlet Container 레벨. Spring 컨텍스트 밖에서 동작 (인코딩, CORS 등)
- Interceptor: Spring MVC 레벨. Spring 빈 주입이 가능해서 QueueService 같은 걸 바로 사용 가능
- 토큰 검증은 QueueService(Spring 빈)를 써야 하므로 Interceptor가 적합

## Q9. 대기열 시스템의 모니터링

**[질문]**
대기열을 운영에 배포했다고 가정할게요. 장애가 발생하기 전에 이상 징후를 감지하려면 어떤 지표를 모니터링해야 할까요? 가장 중요하다고 생각하는 지표 2~3개를 골라보세요.

**[답변]**
> 입장 토큰의 수.

**[후속 질문: 토큰 수의 이상 방향]**
입장 토큰의 수가 많아지면 문제인가요, 적어지면 문제인가요?

**[답변]**
> 많아지면

**[후속 질문: 왜 문제인가]**
왜 많아지면 문제일까요?

**[답변]**
> 소화가 안되고 있다는거지.

**[후속 질문: 대기열 자체의 이상 징후 지표]**
나머지 1~2개, 대기열 자체의 이상 징후를 감지할 수 있는 지표는?

**[답변]**
> 모르겠어.

**[정리]**
대기열 시스템 핵심 모니터링 지표:

| 지표 | 이상 신호 | 의미 |
|------|----------|------|
| Queue Depth | 급격히 증가 | 유입 > 처리량, 스케줄러 이상 가능성 |
| 활성 토큰 수 | 계속 쌓임 | 하류 시스템 병목 or 유저 이탈 |
| 스케줄러 Health | 1분 이상 미실행 | 대기열 전체 정지 |
| Token Conversion Rate | 급격히 하락 | 유저가 주문 포기 → TTL/UX 문제 |

Queue Depth와 스케줄러 Health는 장애 전조를 잡는 핵심 지표, Token Conversion Rate는 비즈니스 건강도를 보여주는 지표.

**[후속 질문: Queue Depth 증가는 단순히 주문이 많은 것 아닌가]**
> 대기 인원이 증가하면 그냥 단순히 주문이 많은거라고 볼 수 있는거 아니야?

**[정리]**
Queue Depth 단독으로 판단하면 안 된다. 핵심은 **증가 속도**와 **다른 지표와의 상관관계**:
- 대기열 쌓이는데 토큰 발급 정상 → 유입 증가 (정상)
- 대기열 쌓이는데 토큰 발급 멈춤 → 스케줄러 장애
- Queue Depth + 스케줄러 실행 여부 + 토큰 발급 수를 함께 봐야 정상/이상을 구분할 수 있다.

**[후속 답변]**
> 아 대기 인원이 점차 증가하면 어 이상하다...? 하면서 스케줄러 실행되는지 확인하고, 입장 토큰이 잘 소비되는지, 실제 주문 흐름 잘되는지 확인해야하는구나.

모니터링의 핵심: 지표 하나만 보는 게 아니라 연쇄적으로 따라가며 원인을 좁히는 것.

```
Queue Depth 급증 감지
  → 스케줄러 정상 실행 중인가?
    → Yes → 토큰은 발급되는데 소비가 안 되나?
      → 주문 API 응답 시간 증가? PG 장애?
    → No → 스케줄러 장애! 즉시 대응
```
