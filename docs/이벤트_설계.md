# 이벤트

## 요구사항

### 1. 비즈니스 흐름을 Application Event로 나누기
애플리케이션의 주요 로직과 부가 로직 등 이벤트 기반으로 분리할 수 있는 로직은
`ApplicationEvent`로 분리한다.

### 2. Kafka 적용 시 상품 좋아요, 판매량, 조회 수를 product_metrics로 관리
Kafka를 사용하여 `상품 좋아요`, `판매량`, `조회 수`를 수집하여 `product_metrics`로 관리한다.

### 3. 선착순 쿠폰 발급 기능을 구현한다.
Kafka를 사용하여 선착순 쿠폰 발급 기능을 구현한다.
발급 요청 -> 수량 확인 -> 중복 발급 확인 -> 발급

## 추가 정보
좋아요수, 판매량, 조회수를 집계하는 테이블 명칭 = `product_metrics`
쿠폰 발급 요청 이벤트 = `coupon-issue-requests`
컨슈머는 event의 멱등 처리를 보장하기 위해 `event_handled`로 처리하는 이벤트를 관리함
프로듀서는 event의 멱등 처리를 보장하기 위해 메시지에 eventId 를 포함하여 전달.
프로듀서는 이벤트 발행 유실을 막기 위해 outbox pattern을 사용하여 발행할 메시지를 저장하고 스케쥴을 기반으로 이벤트를 발행
outbox 테이블을 기반으로 메시지를 발행하는 경우 발행 실패를 위해 재시도를 수행한다. 메시지에 재시도 횟수를 추가해서 무한 재시도를 방지하고 최대 재시도 횟수를 추가한 경우 수동 처리를 진행한다.

## 기능별 주요 로직 / 부가 로직 분리

- 주요 로직: 실패 시 비즈니스가 성립하지 않는 로직
- 부가 로직: 실패해도 비즈니스에 영향이 없는 로직

| 도메인 | 기능 | 주요 로직 | 부가 로직 |
|--------|------|----------|----------|
| 주문 | 주문 생성 | 주문 생성, 재고 차감, 쿠폰 사용 | 판매량 Outbox 저장 |
| | 주문 취소 | 주문 취소, 재고 복원, 쿠폰 복원 | - |
| 결제 | 결제 승인 | 결제 상태 처리, 주문 완료 | - |
| | 결제 거절 | 결제 상태 처리, 주문 취소 | - |
| 상품 | 상품 조회 | 상품 반환 | 조회수 Outbox 저장 |
| | 상품 수정 | 상품 정보 변경 | 캐시 무효화 |
| | 상품 삭제 | 상품 삭제, 좋아요 정리 | 캐시 무효화 |
| | 재고 차감/복원 | 재고 변경 | 캐시 무효화 |
| 브랜드 | 브랜드 수정 | 브랜드 정보 변경 | 캐시 무효화 |
| | 브랜드 삭제 | 브랜드 삭제, 상품 삭제, 좋아요 정리 | 캐시 무효화 |
